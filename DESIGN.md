# Sidequest: Design Document (v2 direction)

Status: draft, actively being developed. This document describes a planned architectural and product direction, not the current shipped state. Where it diverges from what exists in `index.html` today, the current code is the v1 baseline and this document is where v2 is being decided before implementation starts.

## Why this document exists

Sidequest is changing in two ways at once: how it's built (single self-contained file to a multi-file static site) and what it is (a plain planner to a planner with a gamification layer). Both changes are substantial enough to warrant deciding the shape of things before writing code, rather than discovering the shape through implementation. This document is that record.

## What Sidequest is (unchanged)

Sidequest is a project planner for someone juggling several side projects at once: a backlog of tasks, each broken into steps, scheduled into blocks (renamed Sprint/Iteration/Phase/Week per user preference), with a burndown chart tracking progress against a plan. Projects have their own pace, start date, and notes. A parking lot holds ideas not ready to become projects yet. Decisions can block launch-critical steps. Completed and removed items go to an Archive, not straight to deletion.

**This model does not change.** The task/step/block data structure, the burndown math, the Backlog/Candidates/Parking-lot/Archive workflow, and the terminology-flexibility feature are the working core of the app and are considered done and good. Any new work (architecture or gamification) builds on top of this model or reads from it; it does not replace, duplicate, or route around it.

## What's changing: distribution and architecture

### Decision: drop Claude Artifact support (and any AI-tool library-item consideration)

Sidequest will no longer be distributed or maintained as a Claude Artifact, or as a "library item" for another AI chat tool. This was a deliberate trade, made explicitly (2026-09-21), not an accidental casualty of the architecture change. **This part of the decision is already in effect today**, independent of whether the multi-file rebuild described below has happened yet — it governs the current single-file v1 code too, not just the planned v2:

- An Artifact must be one self-contained HTML file with everything inline. Splitting the app into logical files/modules with a shared design-token source is incompatible with that constraint.
- The original reason Sidequest was pursued as an Artifact was distribution and reach through Claude's user base, not a belief that the artifact sandbox made the planner itself better. Once the sandbox's constraints (single file, no build step, restricted CDN allowlist, no `window.claude`/capability APIs, no reliable persistence on the Claude mobile app) stopped being worth the reach they bought, dropping them was the right call.
- Practical effect: no more publishing to a claude.ai artifact link. `assets/` and repo-only icon files are no longer "extras that must be optional" — they're just normal project assets now. External scripts are no longer restricted to Claude's CDN allowlist. `window.claude`/`window.storage` are irrelevant; there was never a real API by that second name, and the real one (`db`) is off the table along with the rest of the artifact model.
- Also effective immediately, in the current v1 code: no user-facing mention of Claude, an AI, an artifact, or a library item anywhere in `index.html` or `README.md`, including generic/hedged phrasing about "apps that embed a web page." A mobile-storage warning was written and then removed the same day (2026-09-21) once this became the settled direction — see `sentinel-notes/storage-persistence-design-brief.md`'s "Superseded" section. The underlying platform fact that warning described (an embedded webview can lack `localStorage` access) has not changed; the decision is that it's no longer worth designing or writing around, given Sidequest's narrowed distribution surface.

### Decision: static multi-file site, still no backend

Sidequest becomes a normal small static site: separate HTML/CSS/JS files (structure to be decided — see Open Questions), served from GitHub Pages exactly as today, with **no server-side code and no database.** This is not a "web app with a backend" in the sense of accounts, sync, or a server process — it's the same static-file model Sidequest already uses, just organized as more than one file.

Consequence: **persistence does not change.** Still `localStorage`, still per-browser, still no cross-device sync, still the same backup/restore workflow. No in-app warning exists anymore about embedded/in-app browser contexts (removed 2026-09-21, see the decision above) — but the underlying "a browser is required, `localStorage` doesn't sync" fact still applies to anyone using the GitHub Pages site on multiple devices; there's just no copy calling that out explicitly.

### Decision: shared design-token source of truth

Currently, design tokens are a `:root` CSS custom-properties block inside the single `index.html` file. In the multi-file structure, this becomes an actual shared file (e.g. `tokens.css` or similar) that every component/module references, rather than one block sitting at the top of one big file. This is a natural consequence of splitting into multiple files, not a new idea layered on top — the current token *values* and *naming* are expected to carry over; the mechanism they live in changes.

**Progress (2026-09-21): CSS split complete.** `css/tokens.css` (the `:root` custom-properties blocks, light/dark) and `css/styles.css` (everything else) now exist as real files, linked from `index.html` via `<link rel="stylesheet">`. No values or selectors changed, byte-for-byte content moved as-is. `index.html` still contains the markup and (for now) the entire JS in one inline `<script>` block — the JS module split is a separate, not-yet-started phase (see below). Verified with real Playwright screenshots (desktop light, desktop dark, mobile) served from a local static file server — not just the jsdom test suite, which has no layout engine and wouldn't catch a real CSS loading failure. Zero console/page errors.

**File/module structure, now decided** (was an open question below; resolved 2026-09-21): `css/tokens.css` + `css/styles.css` for styles; an `app/` folder for JS, split by concern once that phase starts (see the confirmed module boundary in the JS-split section below, once written). ES modules (`import`/`export`), not plain global-scope scripts — the real tradeoff (ES modules refuse to load over a plain `file://` URL, so "double-click index.html to open it locally" stops working; the page must be served, e.g. via GitHub Pages or a local dev server) was confirmed acceptable.

## Claude Artifact parity version (2026-09-23, reopens a prior decision)

### This partially reopens the 2026-09-21 "drop Claude Artifact support" decision

The decision above ("Decision: drop Claude Artifact support") remains in effect for Sidequest's **primary, public-facing distribution**: the GitHub Pages multi-file web app, with no Claude/AI mentions anywhere in its user-facing copy (`claude-mentions`), no artifact-sandbox constraints designed around, and no publishing to a shared claude.ai artifact link. That has not changed.

What's new: a **second, separate version** will be built and maintained specifically to run as a Claude Artifact, using Claude's `db` capability for persistence instead of `localStorage`. This is not a reversal of the 2026-09-21 decision so much as a narrower, parallel goal: get real cross-device sync (via each user's own Claude account) for people who want it, without reintroducing artifact-sandbox constraints into the main public app.

### Decision: a separate repo directory, not a shared codebase by default

Lives in a directory/repo named `Claude-Sidequest` (or similar), holding a single self-contained HTML file — reviving the pre-2026-09-21 single-file architecture (inline CSS, inline JS, inline SVG logo, no build step), since that's still a hard requirement for the artifact sandbox regardless of what the main app does. The GitHub Pages app remains the multi-file, `localStorage`-based version described above. Both are expected to offer the same features and behavior (parity), just built for two different runtime environments.

### Decision: not shared as a live artifact link — distributed as "bring your own database"

The `Claude-Sidequest` file will not be published as a shared claude.ai artifact link the way earlier handoff notes described (a link anyone could open). Instead, users are instructed (via that directory's own README) to download the HTML file from GitHub and ask Claude to publish/save it as their own artifact. The intended effect: each user ends up with their own artifact, under their own account, with its own isolated `db` store — not shared with the app's maintainer or with other users.

**Open question, not yet verified:** the `db` capability is granted at *publish time* via the Artifact tool's `capabilities` field — it is not something a page's own HTML/JS can request or activate on its own by virtue of containing certain code. Whether asking Claude ("please save this as an artifact") reliably results in Claude recognizing the intent and opting into the `db` capability specifically is not guaranteed by instruction text alone; it depends on Claude reading and acting on whatever guidance the file/README gives it at publish time. This needs real testing (upload the file to a fresh Claude conversation, ask for it to be published as an artifact, confirm `db` was actually granted and works) before this distribution model can be considered reliable, not assumed to work from design intent alone.

**Mechanism confirmed 2026-09-23 (via the `artifact-capabilities` skill and the `ArtifactData`/`Artifact` tool contracts), correcting the framing above in one respect:** publishing and sharing are genuinely separate actions. Publishing alone creates a hosted artifact with its own persistent `db`, visible only to the person who published it, by default — nothing further ("sharing") is needed for the intended one-user, cross-device use case. `db` itself, once declared (`capabilities: {db: {}}`), defaults to a **shared, not per-user-private**, document store scoped to that one published artifact: any signed-in viewer with interact/edit access to that specific artifact reads and writes the same documents. True per-viewer-private data is possible but requires *also* declaring the `user` capability and using the `data/users/<id>/` path convention — extra work, not the default.

**Decision (2026-09-23): use `db` in its plain default (shared) shape — no `user` capability, no private-path work.** Reasoning: each user's data is already private in practice, because their published artifact's link is known only to them until *they* choose to share it — privacy comes from the link not being shared, not from access-control engineering. This has a deliberate, accepted side effect: **if a user later shares their published Claude-Sidequest link with someone else and grants them edit access, that second person now reads and writes the same `db`, and the two of them are functionally using it as shared multiuser project-management storage against the original owner's database.** This is being kept as a "comes for free" feature, not engineered around, on the reasoning that it's a genuinely useful side effect of the platform's normal sharing model, not a bug. **Real limitation that must be documented prominently wherever this version is described (README, in-app help): `db` has no transactions and is last-write-wins with no merge** — two people editing the same project/task/decision/step at the same time will silently clobber each other's changes with no conflict warning. This must be framed as a known, accepted constraint of casual/small-scale sharing (e.g. "don't have two people editing the same task at the same moment"), not hidden or promised away as real collaboration-grade sync.

### Decision: shared core logic, storage layer abstracted

The task/step/block/burndown data model, and the view/business logic built on it (`app/state.js`, `app/model.js`, etc. in the web app), should not be maintained as two independently-evolving copies. A storage abstraction is needed so the same core logic can read/write either `localStorage` or `db` depending on which build it's compiled/assembled into. Exact shape (a thin adapter interface both storage backends implement; a build step that inlines the web app's modules into one file for the artifact version; something else) is not yet decided.

**Real complexity flagged 2026-09-23, not yet scoped:** this is not a simple "swap which storage API gets called" abstraction. `localStorage` is synchronous; `claude.use("db")` and every `db` read/write are asynchronous, and the capability namespace itself may resolve `null` (not served as a published artifact, not granted, or failed to load — indistinguishable by design) at an unpredictable point after the page's first script execution, never during it. The current `app/state.js` load/save path is written assuming synchronous, always-available storage. Making it work against `db` means either restructuring that path to be properly async-and-null-tolerant for both backends, or writing a synchronous-looking facade over the async `db` calls (e.g. an in-memory cache hydrated once `db` resolves, written through on every save) — a real design decision, not a mechanical adapter swap. Scope this properly before estimating the build step as a one-time, low-effort bridge.

**Solved, 2026-09-23 (design decided, not yet implemented).** Read `app/state.js` directly: `state` is a single module-level `export var state = load();`, read synchronously by property (`state.tasks`, `state.settings.theme`, etc.) across all 7 other `app/*.js` modules, likely hundreds of call sites in total. Rewriting every read site to be async-aware would be a huge, high-risk rewrite touching almost the entire app. The actual fix is much narrower, because every one of those hundreds of reads goes through the same single object reference, and only two functions (`load()`, `save()`) ever touch storage directly — the fix lives entirely inside `state.js`, at that boundary, and nowhere else:

1. **Boot renders immediately, storage resolves in the background.** On startup, `state` starts as `defaults()` (or a cached last-known value) so the page never blocks waiting on an async capability. Storage resolution (`db` or `localStorage`) happens asynchronously afterward; once resolved, if real saved data exists, the existing `setState()` swaps `state`'s real content in and triggers a re-render.
2. **`save()` stays a synchronous-looking call from every existing call site** (`changed()`, etc. — zero changes needed there). Internally, it dispatches the actual write asynchronously without the caller awaiting it; the `db`-backed implementation debounces/coalesces if a write is already in flight.
3. **The adapter interface is small**: `adapter.load(): Promise<rawStateOrNull>`, `adapter.save(rawState): void` (fire-and-forget internally). The `localStorage` implementation resolves near-instantly; the `db` implementation awaits `claude.use("db")`, treats `null` (capability unavailable) as a graceful fallback to in-memory/session-only operation, and does the real async read/write.

**Consequence, and the resulting UX decision:** `model.js`, `views.js`, `dialogs.js`, and `app.js` need zero changes — they keep reading `state.tasks` synchronously forever. The only new, real behavior is a brief window on the `db`-backed artifact version between "page rendered with defaults" and "real saved data swapped in." **Decided 2026-09-23: cover this with a simple splash/loading screen** (blank interface, then a loading indicator, styled with the future gamification aesthetic in mind — see the gamification section below) rather than a bare flash-of-defaults-then-swap. On a genuinely fresh artifact with no saved data yet, this means the loading screen resolves into the existing sample-data first-run experience, not an empty state.

**Splash screen also extends to the web app, gated by a new setting.** The web app (`localStorage`) has no technical async gap to cover — this is purely a visual-consistency choice, not a necessity, so it must not be forced on unconditionally. Decided: add a settings toggle (default on, for visual parity between the two versions) that lets a user turn the splash off on the web app specifically, since there it's an artificial delay rather than something covering real latency. The artifact version keeps it on by necessity for the actual async gap; whether the same toggle should also apply there once real data has loaded at least once is an open detail, not yet decided. Scope for now: keep the splash simple (per the user's explicit instruction) — this is not the place to build out full gamification visuals, just a small, on-brand loading moment.

**Confirmed 2026-09-23: publishing this artifact needs `capabilities: {db: {}}` declared at publish time, and nothing else** (no `user` capability, per the decision above). The bundled HTML file's own code cannot force this — whoever/whatever publishes it must actually declare it. This sharpens, rather than resolves, the open question above: the file/README instructions need to reliably get Claude to declare exactly `db` (not more, not less) when a user asks for it to be published. Still needs the real test described above before being trusted.

### Build step: implemented 2026-09-23 (concatenation, not the storage swap yet)

`scripts/build-artifact.js` (run via `npm run build:artifact`) produces `Claude-Sidequest/index.html` from the same `app/*.js` and `css/*.css` sources the web app uses. Deliberately a small custom script, not a real bundler (esbuild/Rollup/webpack) — confirmed with the user given this project's zero-npm-dependency codebase and its small, closed, dependency-free module graph (2145 lines across 9 files, no external packages, only relative imports between them).

**How it works:** concatenates the 9 `app/*.js` files in dependency order, strips every `import`/`export` statement (verified against real multi-line import lists, not just the single-line case first assumed — an early version of the script missed these and shipped a `SyntaxError: Cannot use import statement outside a module`, caught by real Playwright testing, not by the build succeeding), and wraps the result in an IIFE. Works correctly because the whole codebase uses only `function`/`var` declarations (confirmed: zero arrow functions, zero top-level `const`/`let`) — hoisting makes concatenation order safe for declarations regardless of the app's real ES-module dependency graph, including its one genuine import cycle (`state.js` <-> `views.js`/`app.js`, already handled deliberately in `app/app.js`'s own boot-sequence code via a `Promise.resolve().then()` deferral, predating this build step). CSS (`css/tokens.css` + `css/styles.css`) is inlined into a `<style>` block the same way. The script fails loudly (throws, does not write output) if `app/` ever contains a file not listed in its `MODULE_ORDER`, or if any import/export syntax survives stripping — verified this actually catches the class of bug above.

**Verified 2026-09-23 with real Playwright testing** (not just "the script ran without error"): the bundled `Claude-Sidequest/index.html` served over http, loaded in a real browser, zero console/page errors, correct initial render (visually confirmed against a screenshot, pixel-identical to the multi-file web app's own), and a real interaction test (clicking a nav tab actually switches the view). `npm test` (the jsdom suite against the *source* `app/*.js` files, unaffected by this build step) still passes 64/64.

**Explicitly NOT yet done, so don't assume `Claude-Sidequest/index.html` is publish-ready:** `state.js`'s `load()`/`save()` are concatenated completely unmodified — the bundle still calls `window.localStorage`, not `claude.use("db")`. The storage-adapter swap (see the "Solved" design above) and the splash-screen UI are separate, not-yet-implemented pieces of work. Running the build today produces a correct, working *local-storage* single-file app, which is a real, useful checkpoint (proves the concatenation mechanism itself is sound) but is not the actual Claude Artifact target yet.

### Named cost: ongoing parity maintenance

Every future feature or fix needs to land in both versions to avoid drift. This is a real, recurring cost, not a one-time setup cost — worth a defined process (e.g. a parity checklist, a periodic audit) rather than an implicit expectation that it'll just be remembered each time.

### Naming and scope of the no-Claude-mentions rule

The existing `claude-mentions` rule (no Claude/AI mentions anywhere in user-facing copy) was written for the single, unified app. It should be understood as scoped to the main GitHub Pages app's own user-facing copy going forward — the `Claude-Sidequest` directory's own README/instructions will necessarily mention Claude, since using that version requires uploading a file to Claude and asking it to publish an artifact. This is a carve-out for that directory specifically, not a reversal of the rule for the main app.

## What's changing: per-project scoping for decisions, milestones, and the Launch page

### Problem, found via user testing (2026-09-21)

Decisions, milestones, and the Launch checklist ("kofi" page, internally named after the user's own Ryewired Ko-fi fundraising campaign — a real, specific example of the underlying problem, not just a hypothetical) are currently global and shared across every project in the app, with no per-project scoping at all. This is one underlying data-model gap surfacing in three places, not three separate problems:

- `state.decisions` (index.html) is one flat list. Any decision, regardless of which project it's conceptually about, appears on the single shared Launch/"kofi" page. Its only field even indirectly related to a project is an optional `step` link (a decision can link to a specific step; if it does, the step's task's `.project` is the only way to infer which project the decision is "about"). A decision with no linked step, which the dialog explicitly allows, has no relationship to any project at all.
- `state.milestones` is the same shape of gap, one level simpler: entries only ever have `text` and `date`. There is no project field and no linking mechanism of any kind (not even an optional step link like decisions have), so a milestone can never be associated with a specific project today, full stop.
- A step's `kofi` flag (marking it "Launch-critical") works the same way as decisions: any task from any project can have a step flagged for the Launch checklist, and it all lands on that one shared page.
- Concretely: the user is building a specific fundraising campaign called "Ko-fi" as a subtask of their Ryewired project. Because Sidequest's built-in Launch-checklist feature is also internally called "kofi," and because it's global rather than scoped, there's a real risk of the two concepts bleeding into each other, and more generally, any project's launch-critical steps/decisions currently show up mixed in with every other project's on one page, with no way to keep them separate.
- The confirmation message a user sees after adding a decision ("Decision added on the Launch page") is accurate today, but doesn't convey that this is one page shared by every project, which is why a newly created decision can feel like it "disappeared" if the user expected something project-specific.
- The New Decision and New Milestone dialogs cannot offer a "which project" picker today, because neither underlying data structure has a field to hold that answer yet — this isn't a missing UI control, it's a missing column.

### Decision: scope decisions, milestones, and the Launch checklist per-project

Rather than a copy-only fix, this becomes a real data-model change, deliberately deferred for proper design work rather than implemented ad hoc (2026-09-21). Treating decisions and milestones as one combined design effort, since they're the same underlying gap (a small, previously-flat sub-object needing project association) rather than two unrelated features. Needs answers before implementation:

1. **Does each project get its own Launch page, or does one shared page filter/group by project?** A separate page per project changes navigation/pinning (currently one `kofi` pin in `state.pins`); a filtered single page keeps one page but adds a project-selector or grouped sections.
2. **Does a decision or milestone require a project, or can either stand alone** (e.g. for the "Next project" placeholder, which isn't a real named project yet, or a milestone that's genuinely about the whole planner rather than one project)? `decisions` currently link to a step (`step: "..."`), not directly to a project — project scoping would likely be derived from the linked step's task's project, but decisions can also exist with no linked step at all (`step: ""` is valid), which needs its own answer. Milestones have no existing link of any kind to build on, so this is a more open question for them: a direct `project` field added to the milestone itself is the more obvious shape, rather than trying to invent an indirect link the way decisions have one.
3. **Migration for existing saved data.** Every current user's saved decisions, milestones, and launch-flagged steps have no project association today. `normalize()` needs a real default/backfill strategy (e.g. infer project from the linked step for decisions, an explicit "unassigned"/general bucket for milestones with no obvious project to infer) so existing data doesn't break or silently vanish.
4. **Pinning behavior.** If Launch becomes per-project, does the pin model change (one pin per project's Launch page) or does the single `kofi` pin become a launcher to a project-picker?
5. **Timeline display.** Milestones currently render on the single shared Timeline regardless of project. If milestones become project-scoped, decide whether the Timeline still shows all of them together (now labeled by project) or whether project-scoping changes how/where they render there too.

This is a v1 architecture fix (the current single-file app), independent of the v2 pivot (multi-file rebuild, gamification) described below — it should likely be designed and possibly implemented before or during the v1 backlog work, not bundled into the v2 rebuild.

## What's changing: gamification layer

### Decision: HP is pure emotional flavor, not a real stakes mechanic

Hitpoints/health, inspired by Habitica's HP mechanic, will exist in Sidequest as a **prominent, emotionally resonant readout**, not a real loss condition. Explicitly decided (2026-09-21): no actual penalty, no data loss, no feature lockout tied to HP reaching zero. It should *feel* like it matters in the moment (visually, emotionally) without ever punishing the user in a way that damages their actual planning data or blocks their work. This is a deliberate divergence from Habitica's model, chosen because Sidequest's existing audience and tone (calm, low-pressure, side-project planning) doesn't fit a genuinely punishing mechanic.

What "prominent" means in practice (visual placement, exact triggers) is still open — see below.

### Reference points (researched 2026-09-21, not yet decided which ideas Sidequest adopts)

- **Habitica**: the most mechanically deep of the three references. Public/general knowledge (not independently re-verified against Habitica's own docs in this session due to a fetch access issue): HP decreases when scheduled "Dailies" are missed, and reaching 0 HP triggers a real, consequential loss (historically framed as a `"death"` state with a real setback). Also has XP/leveling, gold, classes with skills, and party/guild social accountability. **Sidequest is explicitly not adopting the real-consequence half of this model** (see decision above) — HP as flavor only.
- **Do It Now**: avatar-based RPG framing. Completing tasks grants XP and "gold," gold buys user-defined real-world rewards. Has difficulty/importance ratings per task, auto-fail for overdue items, skill-binding (a task can feed a specific character skill/stat), and calendar/chart-based progress visualization.
- **LifeRPG**: similar RPG framing (quests = daily duties, leveling, skills), notable mainly for flexible task organization by multiple priority dimensions rather than one axis, and an energy-based task categorization.

### Open questions to resolve before implementation

These need real decisions, not defaults, before the gamification layer can be built:

1. **XP/Score mapping.** Should XP per completion reuse the existing burndown `weight()` concept (a task's step count, minimum 1) directly, so game-score and burndown accounting are always the same number? Or should score be a separate, independently-tuned value?
2. **HP trigger and readout.** What specifically decreases HP — the existing `isLate()` overdue concept? Something else? Is HP a single global number, or per-project? What does the "prominent" readout actually look like (a top-of-page bar like a game HUD, a badge, something else)?
3. **Reward triggers.** Visual/audio effects on completion — which completion events trigger them (a step, a task, a whole project)? Is this the cheapest, lowest-risk gamification element to prototype first, independent of the bigger architecture change (nothing about a completion animation requires the multi-file rebuild)?
4. **File/module structure.** ~~What the actual split looks like...~~ Resolved 2026-09-21 for CSS (`css/tokens.css`, `css/styles.css`, done). For JS: `app/`, split by concern, ES modules — confirmed boundary: `state.js` (state/storage/normalize/defaults/sampleData), `dates.js` (date math/formatting), `model.js` (task/project/burndown query helpers), `dom.js` (el/on/notify/small DOM utilities), `views.js` (all renderX page functions), `dialogs.js` (form dialogs + modal), `search.js`, `chart.js` (drawChart/rangeBlock), `app.js` (boot, renderView dispatch, event wiring — the entry point importing everything else). Not yet implemented — this is real, carefully-sequenced work given the current code is one tightly-coupled IIFE with no existing module seams; each of these 8 files needs real, correct `import`/`export` wiring, not just a mechanical cut-and-paste.
5. **Naming/theming.** Whether "Hitpoints" and RPG terminology apply everywhere or are optional/skinnable, and how they interact with the existing Block/Sprint/Iteration/Phase/Week terminology flexibility, is undecided.

## Decision log

- 2026-09-21: Investigated cross-device/cross-app persistence options (`window.storage`, Claude `db` capability, a flat-file DB). Concluded none fit Sidequest's goals without unacceptable tradeoffs (Claude-only lock-in, shared storage ceiling, architecture mismatch). Decided to keep `localStorage` and instead document the Claude-mobile-app limitation clearly (shipped same day, see `sentinel-notes/TODO.md`'s Done section, `mobile-storage-warning`).
- 2026-09-21: Reconsidered whether Sidequest is worth pursuing as "just another web planner" given the crowded market. Concluded the real differentiators (solo-project burn-down modeling, terminology flexibility, decision-linked launch checklist) are product-design choices independent of Claude-artifact distribution, and are worth continuing to build regardless of distribution model.
- 2026-09-21: Decided to pivot to a multi-file static site (dropping Claude Artifact support) with an added gamification layer, HP as flavor only. This document created to track that pivot's design decisions before implementation.
- 2026-09-23: Decided to also build a separate, single-file Claude Artifact version (`Claude-Sidequest` directory) using the `db` capability for real cross-device persistence, distributed as "download from GitHub and publish it yourself" rather than a shared link, so each user gets their own isolated database. Partially reopens the 2026-09-21 artifact-support decision for this one, separate, parallel version — the main GitHub Pages app's own no-Claude-mentions and no-artifact-constraints decisions remain unchanged. See "Claude Artifact parity version" section above; several open questions (whether `db` is reliably granted this way, the storage-abstraction shape, parity-maintenance process) are not yet resolved.
- 2026-09-23: Investigated the actual `db`/`Artifact` capability mechanism directly (the `artifact-capabilities` skill, the `ArtifactData` tool contract). Confirmed publishing and sharing are separate actions, and that `db` defaults to shared-not-private scoping per artifact. Decided to use `db` in its plain default shape (no `user` capability, no private-path work) — privacy comes from not sharing the link, not access-control engineering — and to deliberately keep, rather than engineer around, the resulting side effect that a shared link becomes ad hoc multiuser storage against the owner's database if they choose to share it and grant edit access. This must be documented as a known limitation (no transactions, last-write-wins, no conflict resolution) wherever the Claude Artifact version is described. Also flagged that the storage abstraction needed to keep one shared codebase is a real async-vs-sync, possibly-null design problem (localStorage is sync and always-available; db is async and can resolve null), not a simple interface swap — not yet scoped.
